# The 2026-09-15 build's offsets: what was moved, and how each was chosen

The 2026-09-15 title update (Steam build 25120584) moved nearly every
engine address this framework patches. This document records the state
of that port after this branch's work: which addresses were already
right, which were still pointing at the pre-update build, how the two
were told apart, and why each disputed address was settled the way it
was. The short version of the method: **an address is only ever judged
against the binary it must live in, by what the code at that address
actually is — never by name, and never by trust.**

Three populations of addresses meet here:

1. **The fork point.** What this tree carried before the update: the
   addresses of the pre-update build (24669148), inherited from the
   upstream project.
2. **The 2026-09-16 re-pin.** This fork's own answer to the update,
   committed that day: a sweep that re-derived most constants against
   the new build.
3. **The Immersion Suite port.** The Wildlands Immersion Suite fork's
   independently validated port of the same update — 101 addresses
   checked against the new build with zero unexplained mismatches, and
   running shipped to players since.

## 1. Finding what the 2026-09-16 sweep missed

A define whose value still equals the fork-point value is a pre-update
address by definition — whatever the surrounding code does, those bytes
moved. That is the one case where a value can be replaced without
further questions, provided the replacement is validated for the same
named thing.

Fifty-two defines were still at their fork-point values: the whole
domino cluster, the havok rigid-body vtables, the entity controller
vtable, two npc globals, and parts of scene and ui. All 52 were replaced
with the Immersion Suite port's validated values. The hit pair moved
together — `HIT_SITE` is a call site and `HIT_ORIG_CALL` the function it
calls, so they can only ever be re-pinned as a pair. (The hit site also
carries no byte guard of its own; on the new build, with the old site,
`ShHitHookInstall` would have patched whatever moved into that address.
Both halves of that hazard are closed by this change.)

The classification needed a fourth data point besides the two values:
the fork-point value itself. A name-join between two forks' headers is
not enough, because a define that differs from the Immersion Suite's
value may be *another sweep's correct answer* rather than a stale one —
which is exactly what the 2026-09-16 re-pin turned out to be, and what
the next section had to adjudicate.

## 2. Adjudicating against the 2026-09-16 re-pin

Eleven defines disagreed with the Immersion Suite port while not being
at their fork-point values — this fork's own re-pins. Twelve more
(ammocap, playmode, the npc population manager) had no counterpart to
compare against at all. Each was identified in the current build by
what the code there actually is, using the pre-update binary's
functions as the semantic reference. Four techniques carried the work:

### Thunk chains first

Most "functions" in this engine's hot paths are `E9` jump-table thunks:
five bytes that jump at the real implementation. Comparing a thunk in
one build against an implementation in another compares nothing. Every
code address was resolved through its chain before any comparison —
and one phantom disagreement dissolved immediately: **`CTW_START`**.
The Immersion Suite pins the thunk (`0x2827F10`); this fork pins the
thunk's *target* (`0x13D122D0`). Same function, two conventions, both
correct. Kept as found.

### Masked shape against the old build

For a real function, the pre-update binary's body is the ground truth.
Both candidates' instruction streams (immediates and far displacements
masked) were compared against the old body. **`SH_APPLY_DAMAGE`** fell
to this: the old function's first eighty instructions match the
Immersion Suite's candidate at 1.00 and this fork's pinned thunk
target at 0.01 — the re-pin had found an unrelated function, and the
health damage call was being queued into the wrong engine code.
Replaced.

### Tail calls for same-shaped families

The scene wrappers (`F_SCENE_FLIP`, `_RENDER`, `_RESIZE`, `_TICK`) are
deliberately shaped alike — their prologues and bodies are identical
for dozens of instructions, so shape cannot separate them. But each
wrapper exists to forward through one call, and the *forwarded target*
is the family member's real name. Building the identification matrix
over those tails settled all four plus the allocator: the Immersion
Suite values are the 1.00 successors of the old functions, while the
re-pins had landed two functions from outside the family under
`_RENDER` and `_RESIZE`, and the set-resolution and set-context pair
under `_FLIP` and `_TICK`; the allocator matched at 0.03. All six
replaced (`F_ALLOC_CTX` in both scene and ui).

### The module's own guard, run offline

`playmode` verifies a hook site by scanning the function's first bytes
for the instruction that loads its own log line's address, rip
relative. That scan needs no runtime: run as a byte scan over the
file, it finds the proof references at exactly the documented offsets
(+0x25 in `SetCurrentGameMode`, +0x92 in `CreateGameMode`). Both sites
and both proofs verified. The same offline check style confirmed
ammocap's `CAP_RVA`: an `E9` thunk at the address, precisely the form
its installer logs and expects.

(One harness lesson worth recording: a linear disassembly from a
function's start can desynchronize mid-body and miss a reference a
byte scan finds. The proof scans here are byte-level for the same
reason the module's own are.)

## 3. The npc population addresses

Three defines in `scripthook_npc.c` had no counterpart anywhere — and
one of them only *appeared* to. The population manager slot
(`RVA_POP_MGR`, `0x4B98FA8`) is carried by the Immersion Suite under
the name `RVA_POPMGR`, and it passed that port's whole-framework
validation; this fork derived its value independently, at runtime, off
the engine's own register calls, with a vtable self-check on the
result. Two derivations, one address: verified. Beyond that, nineteen
of this file's twenty-one defines are byte-identical between the two
ports — including the registry slot this fork decoded off the engine's
call path, which lands exactly on the validated value. The two RE
efforts cross-validate each other throughout this file.

`RVA_CONTEXT` (`0x4B98F98`) is dead by its own comment: the slot holds
float bit patterns in the campaign, the camp/job reading of it crashed
the game, and nothing reads it any more. It stays as a bookmark.

`RVA_RETIRE` was the one true disagreement, and the interesting one.
The pre-update retire is a 173-instruction despawn *action*. This
fork's pin is a 40-instruction action function whose opening guard is
the old function's, restructured by the recompile (the field moved
`+0xC0` to `+0x108`) — and it is marked verified live. The Immersion
Suite's ported value turns out to be a six-instruction boolean guard
that shares the old function's opening lines: a prologue-heuristic
match that caught the wrong member of the family. **This fork's value
is the better one and is kept**; the mis-pin has been reported to the
Immersion Suite side (nothing it ships exercises npc, so it was never
observed there).

## 4. Criteria, in one place

- A define still at its fork-point value is stale; replace it only
  with a value validated for the same named thing.
- A disagreement between two ports is settled by identifying the code
  at each address in the current binary — thunk chains resolved,
  shapes matched against the pre-update body, same-shaped families
  separated by their forwarded calls — never by preferring either
  port.
- A module's own install-time guards are tests: run them offline, and
  a pin that passes its own guard with the documented offsets is
  verified.
- What cannot be checked is left alone and written down, not guessed.

## 5. Verification state

Everything in this document was checked statically against the
shipping binaries of both builds (the pre-update binary preserved from
Steam's depot, and build 25120584 as installed), with the exception of
the runtime-derived notes called out as such (the population manager's
decode, the retire's live verification). The firstperson module's
sites were previously verified byte-exact against the installed build
and re-verified here by resolving the four load-bearing call sites.
